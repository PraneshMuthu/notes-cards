# notes-cards: design

**Date:** 2026-11-26
**Status:** draft, awaiting approval

## Intent

This is a personal recall app for interview prep, used mostly on a phone in spare minutes and sometimes on a laptop.

- **Format:** one card per screen, swiped like Reels or Shorts.
- **A card is a single idea worth recalling,** not a whole problem.
  - Example: "Why is `hold_id` a UUID and not auto-increment?"
- **Sources:**
  - The owner's HLD and LLD study repos.
  - Common DSA interview problems.
  - Topics added later (Python, frontend, …).

**Why:** reading a solution once does not survive to interview day. The app turns what has been read into recall practice, scheduled the way memory works:

- **Retrieval practice:** recall before you see the answer.
- **Spacing:** review just before you would forget.
- **Interleaving:** mix topics.
- **Elaboration:** every answer carries the *why* and an example.

### Goals

- A swipeable feed of mixed-topic cards.
  - It never shows two cards in a row from the same topic.
  - Topics are spread evenly.
- Spaced repetition with the FSRS algorithm.
  - Each card comes back just before it would be forgotten.
  - The gaps grow as the card is remembered.
- Three queues, each also viewable on its own:
  - **Due:** cards whose scheduled review time has arrived.
  - **Forgot:** cards graded "forgot". They return within minutes, then within a day, until they stick again.
  - **New:** cards never studied. Capped per day so that new material never drowns out reviews.
- **Endless after due.** Once due cards are done, the feed keeps going.
  - It shows the weakest cards first (lowest predicted recall).
  - About 1 in 5 cards is new.
  - The same card is never repeated within a short window, except for planned "forgot" relearning steps.
- **Easy to add topics.** Adding a topic means adding one Markdown file and pushing. It is live in about a minute.
- **Feels like an app.**
  - "Add to Home Screen" opens it full-screen on a phone.
  - Once loaded, it works offline.
- **Free.** Zero hosting cost.

### Non-goals

- No multiple users, accounts, sharing or social features.
- No editing cards inside the app. Cards are edited as text files in git.
- No native iOS or Android app, and no app-store release.
- No analytics dashboards beyond simple counts.

### Anti-goals (a failure even if it technically works)

- Cards that are walls of text. Each back must be readable in about 10 seconds.
- A feed that keeps showing the same few cards, or one topic in a long run.
- Losing study progress silently.
- Anything that costs money, or that uses any GitHub account other than PraneshMuthu.
  - Never use the `gh` CLI for this repo; push over SSH only.

## Constraints

- **Hosting:** GitHub Pages from the public repo `PraneshMuthu/notes-cards` (personal account, pushed over SSH).
  - The owner accepts that the content is publicly readable.
- **Stack:** no build step. Static HTML, CSS and plain JavaScript (ES modules), served as-is.
- **Teaching style for card content:**
  - Define jargon.
  - Lead with everyday examples.
  - Keep it short.

|---|---|---|---|

## Design (decided)

### Card files

The cards live in `cards/<topic>.md`, one file per topic, for example:

- `cards/hld-08-bookmyshow.md`
- `cards/dsa-two-pointers.md`
- `cards/python.md`

```markdown
---
topic: HLD · BookMyShow
group: HLD
---

## Why is `hold_id` a UUID, not auto-increment? {#bms-hold-id}
Generated by the Booking service per hold request and stamped on every seat in that hold.
**Why:** needed before the UPDATE runs; no holds table exists to generate it; unguessable.
**Example:** cloakroom token: coat and bag get the same token.
```

- **Front:** each `## ` heading is one card's front.
- **Back:** everything up to the next `## ` is the back, rendered as Markdown.
- **Card id:** the optional `{#id}` gives a stable id. Without it, the id is a slug of the topic plus the front text. Then editing the front resets that card's progress, which is acceptable.
- **`group`:** a top-level bucket (HLD, LLD, DSA, Python, …) that the interleaver balances on.
- **DSA cards are the exception:**
  - The front is the whole problem statement, short.
  - The back is the **pattern**, the **key insight** in one line, and the **time and space complexity**.
  - An optional ~5–10 line code skeleton sits inside a `<details>` block, collapsed by default.
  - The goal is "I see this problem → I know the approach", not memorising code.
- **Card list:** `cards/index.json` lists the card files, because GitHub Pages has no directory listing.

### Scheduling

- The FSRS scheduler is `ts-fsrs`. Its ES module file is downloaded once and committed under `vendor/`.
  - This means no CDN dependency at runtime, so offline works.
- Target retention is 0.9 (FSRS default parameters).
- **Grading after each reveal:**

  | Grade | Meaning |
  |---|---|
  | Forgot | did not recall |
  | Hard | recalled with effort |
  | Got it | recalled |
  | Easy | recalled instantly |

- **Feed order:**
  1. Relearning cards whose short step is up ("forgot" cards coming back).
  2. Due cards.
  3. New cards, up to the daily cap (default 10, set in settings).
  4. When nothing is left: weakest-first. These are cards ordered by lowest current retrievability. About 1 in 5 is a new card, even past the daily cap.
- **Interleaving within that order:**
  - Never two consecutive cards from the same topic.
  - Groups take **equal turns** (round-robin), so a big group like DSA does not crowd out a small one like Python. *(Claude's call: "evenly" means equal turns, not weighted by size.)*
- **When order and mixing collide** *(Claude's call)*: the picker walks the queues in priority order.
  - If the best card would repeat the last topic, it takes the best card from a different topic. It looks first in the same queue, then in lower queues.
  - Back-to-back cards from the same topic are allowed only when one topic is all that is eligible, for example when the topic filter is narrowed to one topic.
  - The feed never stops to show "done". It falls through to weakest-first.
- **No short repeats:** a card shown in the last ~20 cards or ~10 minutes is skipped, except for its own relearning step. If the filtered set is smaller than that window, the window shrinks to half the set.
- **Relearning steps** *(Claude's call)*: ts-fsrs is configured with learning steps `[1m, 10m]` and relearning steps `[10m, 1d]`. A "forgot" card comes back in 10 minutes, then the next day, and then returns to normal FSRS spacing.
- **"Forgot" queue** = cards currently in the FSRS Relearning state.
  - The ✗ counter counts them.
  - In the "Forgot only" view, cards whose step has not arrived yet are shown anyway, soonest first, rather than an empty screen.
- **Daily cap** *(Claude's call)*:
  - "Today" resets at 4 AM local time.
  - The cap is counted per device in v1.
  - New cards shown in endless mode past the cap do not count toward "new left today".
- **Early reviews are recorded normally.** These are grades given in weakest-first mode, before the card is due. FSRS accounts for the elapsed time.

### Screens

```
┌─────────────────────────┐
│ HLD · BookMyShow   12 ⏳ 3 ✗ 5 ✦│   topic chip · due · forgot · new left today
│                         │
│  Why is hold_id a UUID, │
│  not auto-increment?    │
│                         │
│      [ tap to reveal ]  │
│                         │
└─────────────────────────┘
        ↓ after tap
┌─────────────────────────┐
│ …answer, why, example…  │
│                         │
│ [Forgot][Hard][Got it][Easy]│
└─────────────────────────┘
   grade → next card slides up
```

- **Feed** (the default).
- **Queue filter:** All, Due only, Forgot only, or New only.
- **Topic filter:** limit the feed to some groups or topics.
- **Settings:**
  - the daily new-card cap
  - export and import of progress as a JSON file
  - the sync token (phase 2)

### Progress storage

- **Local-first.** It is stored in the browser (localStorage, or IndexedDB if size demands it).
- **What is stored:** an **append-only review log**, plus each card's derived FSRS state.
  - Each log entry records the card id, the grade, a timestamp and the device id.
- **The log is the source of truth.** The state can always be rebuilt by replaying the log.
- **Backup:** export and import of the log as JSON.

### Phase 2 (nice to have): sync between phone and laptop

**Not built in this plan; only designed for** *(Claude's call: the owner called it good-to-have)*. v1 must keep the data shapes below so that phase 2 is purely additive.

- **Where progress lives:** a **separate private repo**, `PraneshMuthu/notes-cards-progress`, written through the GitHub REST API.
- **Auth:** a **fine-grained personal access token** with Contents read/write on that one repo only.
  - The owner creates it once on github.com.
  - It is pasted into Settings on each device.
- **One file per device:** each device writes only its own log file, `logs/<deviceId>.json`.
- **Sync:** pull every device's log, take the union of entries by (card id, timestamp, device), and replay through FSRS.
  - This has no conflicts by design.
- **When it syncs:** on app open, and after every N reviews or when the app goes to the background.
- **Why this over Supabase or Firebase:**
  - It needs no new account.
  - It stays on GitHub.
  - Supabase's free projects pause after a week of inactivity.

### Content for v1

Writing the cards **is part of this plan**, as a second stage after the app works. *(Claude's call)*

- **Order:** the app is built first with a small sample deck, then the real cards are written one topic file at a time, and the owner reviews each file as text.
- **Who writes them:** Claude, from the repos.
- **Source:** each problem's `solution.md`, including the owner's 📝 read-through notes. For the problems the owner worked through by hand, their own write-up comes first.
- **Coverage:** **every** HLD and LLD problem in the repos, including ones not studied yet.
  - Unstudied ones simply sit in the New queue. This matches the owner's ask for a queue of "topics I've never read".
  - Problems already ticked in `HLD/STUDY-PLAN.md` are written first.

Each problem gets about 10–20 cards, covering:
  - the key numbers
  - the main decisions and why
  - the deep-dive resolutions
  - the traps
- **DSA:** about 50 common interview problems, grouped by pattern.
  - Patterns: two pointers, sliding window, binary search, BFS/DFS, heaps, DP, …
  - Problem statements are paraphrased.

## Additions after launch (2026-11-26)

- **Skip / Next:** move on without grading. Nothing is logged. A skipped card stays away for ~10 min, even if its relearning step is due.
- **Bottom navigation:** ‹ Back / Next ›.
  - Back steps through this session's earlier cards read-only, with the answer open.
  - Forward walks back toward the live card.
- **Change grade** (look-back only, the card's latest grade only):
  - Appends a correction entry `{…, r: <replaced t>}`, so the log stays append-only and phase-2 union sync still works.
  - `effective()` drops replaced entries before replay and before counting.
- **Status line on every card,** colour-coded with the grade colours:
  - New (blue)
  - Learning · seen N× today (amber)
  - Review · Nth time · last seen <date> (green)
  - Forgot last time (red)
- **"Forgot"** = relearning, or still learning after the last grade was Forgot. This includes new cards graded Forgot.
- **Top bar:** plain-word counters (Due / Forgot / New). The topic label moved onto the card. The menu shows "Seen X of Y" overall and per group.
- **Deploy:** `.nojekyll` at the root, so GitHub Pages serves the raw card `.md` files.
